# 通用文档与写作规范

七个技能共用此文件。

## 规范读取与修改范围

按技能入口的路由先读当前类型的相关规范，创建或实质重写时读模板。已读且未变化的资料不重复读取；配套资料不触发其他技能，也不要求加载全部资料。

阅读和修改限于本次范围：局部修订只处理相关内容，仅修链接不改版全文。按本技能对应规范补充和组织本次范围内的文档；只审查时提出建议。配套资料缺失时说明影响，继续不依赖它的工作，不声称已完整遵循规范。

只核对改动涉及的规范与引用；保留适用的项目验证要求，不额外增加全库审计或逐句复审。历史原文与有效独有信息按授权范围保留。

## 需求定义与实施规划

按文档或章节的实际作用区分边界，不只看文件名。决定要做什么、对外行为、约束和交付承诺的内容承担需求定义作用，通常是 spec，也可能位于需求说明、设计方案或 plan 中。

编写或修改需求定义时，以用户明确要求、讨论中已确定的内容和适用的既有项目约定为依据。可以整理结构、澄清措辞和展开不改变原意的说明，不得把工程惯例、模板示例、AI 建议或未确认的推断写成已确定的需求、约束或完成条件。候选仍是候选，待决仍是待决；未讨论的内容可以省略，不为完整性补齐章节或要求。

编写或修改需求定义时，先根据已确定的内容完成文档。发现有实际价值的补充建议时，应在完成后主动向用户说明建议的用途和主要取舍，并询问是否纳入。未经确认的新建议默认放在回复中，不提前写入 spec，也不因尚未确认而压下不提；没有有价值的建议时不必凑数。

例如，用户只确定“批量重命名，支持前缀和序号”时，spec 只记录这些已确定的需求。写好后，可以主动询问：“执行前预览可以帮助发现命名错误，你希望加入吗？”操作预览、撤销和失败回滚等建议，由用户决定是否纳入，不提前混入 spec。

用户明确要求在文档中保留候选内容时，标为建议或待决；明确授权设计或补全需求时，可以展开设计，自行提出的部分作为设计提案呈现，不冒充此前已确定的结论。缺失信息实质影响已确定内容的准确表达时，应针对该缺口澄清，不为每个空白逐项确认。

依据 spec 或类似定位文档组织 TODO、plan、roadmap 时，可以自主拆解任务、选择实施步骤、安排依赖和必要检查，并形成可判断的任务完成条件；这些工作不必在讨论中逐项出现。不得借实施规划改变或扩大既定需求、对外行为和交付承诺。发现需要调整需求时提出建议，不直接写成已确定事项。

## 写作

- 先写谁做什么、发生什么变化、还有什么未完成。使用常见词和完整句子，不把正文压成术语串。
- 标题可以简短；正文要交代对象、动作和结果。例如“完成验证闭环”改为“正常输入和单项失败场景均通过”；“实现多后端能力收敛”改为“两个后端现在使用同一份输入配置”。
- README 和使用说明面向初学用户；TODO 写可识别的交付结果；技术文档保留准确术语并解释必要概念；ADR 简短交代理由；AGENTS 可以紧凑，但条件、范围和动作必须明确。
- 每个事实和任务状态只维护一处，其他文档链接过去。没有真实内容不建空文件、空目录或空章节。
- 默认更新当前状态，不追加会话日志、交接摘要、验证报告或重复总结。执行验证不等于保存验证经过。
- 归档的 plan/spec 和旧历史不因写作规则重写。
- 用户明确要求与项目约定优先于默认模板。已授权修改直接执行；只有缺失信息实质影响结果或需要新增授权时才提问。
