# 解释型文案的常见问题

解释型文案用于帮助读者理解对象、概念、关系和原因，例如项目有什么用、流程如何运行、系统如何组成、为什么这样设计，以及存在哪些限制。

按段落承担的作用判断是否需要解释，不按文件类型一概而论。同一份文档可以既有解释设计原因的段落，也有规定接口约束的条目；两者应分别组织表达。

只提供有助于理解与决策的信息，用尽量少的文字交代关键关系。不机械地为每句话添加主语，也不把简短说明写成教程；简洁不能省略影响理解或结果的必要概念、单位、条件和限制。

编写时避免以下六类问题，正反例用于展示表达差异。

## 1. 把规则简写当成解释

**说明：** 用规定式短句描述已有行为或关系，容易让读者分不清这是事实说明，还是需要遵守的要求。解释时写清必要的对象、条件及其关系；涉及操作时，区分程序自动执行的动作与读者需要完成的操作。

**反例：** “部署前创建快照（强制覆盖始终备份）”

**正例：** “部署前创建快照（强制覆盖则会自动备份原有配置）”

**反例：** “切换项目之前保存修改。”

**正例：** 若程序自动保存：“切换项目时，程序会自动保存当前修改。”若需要用户保存：“切换项目之前，请先保存当前修改。”

## 2. 默认读者已经熟悉实现

**说明：** 根据文档的目标读者确定解释深度，不默认其熟悉本项目的实现和隐含约定。写完后从目标读者的位置审阅，不能以作者自己读得懂为通过标准。

**反例：** “本项目用于仿真后处理。”

**正例：** “本项目读取仿真结果中的压力数据，计算并绘制观测点的声压频谱。”

**反例：** “增量导出：使用增量模式导出。”

**正例：** “增量导出：只导出上次导出后新增或修改的文件，适合更新已有副本。”

## 3. 用模糊动作代替具体结果

**说明：** “处理”“优化”“提高扩展性”等表述如果缺少具体对象和结果，就只是把解释留给读者猜测。说明谁对什么做了什么、产生什么变化；解释设计理由时，交代该设计如何带来所述效果，不必展开无关过程。

**反例：** 架构说明中写：“统一处理存储，提高扩展性。”

**正例：** “业务模块通过统一接口读写数据，更换数据库时无需修改这些读写调用。”

**反例：** “退出时如有修改，先处理再退出。”

**正例：** “退出时如有未保存的修改，程序会提示你保存、放弃修改或继续编辑。”

## 4. 用内部术语代替解释

**说明：** 内部名称、数据结构和技术术语不能单独充当解释。介绍用途时使用读者认识的对象和动作；解释架构时可以保留模块名、接口和技术概念，但要说明其职责、关系或采用原因。技术细节是否需要出现，取决于它能否帮助读者理解当前主题。

**反例：** “通过 EventBus 完成模块解耦。”

**正例：** “模块通过事件总线（EventBus）传递消息，发送方无需直接调用接收方。”

**反例：** “通知设置：每项含 type 和 enabled。”

**正例：** “通知设置：选择接收哪些类型的通知。”

## 5. 为了显得完整而过度解释

**说明：** 只解释目标读者理解当前主题所需的信息，避免同义复述、无关背景和不必要的展开。名称已清楚的常见操作无需另加说明；文档中已经讲清的含义也不必换一种说法重复一遍。

**反例：** “退出：使用此选项可以退出当前应用程序，结束本次使用。”

**正例：** “退出”

## 6. 把信息放在不需要它的位置

**说明：** 按读者理解主题的顺序安排信息。概览交代用途或整体关系，具体约束放在对应步骤、接口或概念附近。避免在概览中堆入细节，又让读者在实际需要时返回其他章节查找。

**反例：** 在架构概览中逐项列出请求字段和长度限制，到了接口说明却只写“按要求提交任务”。

**正例：** 架构概览说明“API 接收任务并放入队列，工作进程从队列取出任务执行”；字段格式和长度限制放在对应接口说明中。

**反例：** 在功能介绍中写“导出报告，名称为 1–64 个字符”，实际输入框却只标“名称”。

**正例：** 功能介绍写“导出报告，便于分享分析结果”；对应输入框标“报告名称（1–64 个字符）”。
